## ADR-023 in brief: leader election without trusting clocks

The chart allowed several replicas on PostgreSQL, but every replica ran the full controller set and server-side-applied the same objects with `force`. The decision: only the holder of the Lease `kuben-controller` runs the controllers; every replica still serves the API from its projections. Every Lease write is a compare-and-swap on `resourceVersion`; a candidate treats the Lease as expired only after seeing it unchanged for the lease duration (15 s), never by comparing `renewTime` with its own clock, so skew cannot produce two leaders. The leader renews every 2 s and stops its controllers if renewal fails for 10 s. On shutdown it releases the Lease. Login-throttle windows moved to the database so all replicas share one budget. Read the [blog post](/blog/leader-election-without-clocks/) for the full reasoning.

## ADR-024 in brief: one task runner for two languages

Every package is a Turborepo package, whatever its language, and the cross-language edges are explicit tasks: `@kuben/console#build` → `hub#build`, which embeds the console into the Go binary. Up to 1.2 the Rust crates were packages of Turborepo's native Cargo workspace; since ADR-033 the Go modules of `go.work` take their place, and Go schedules and caches compilation. Bun 1.4 is the package manager, JS runtime and test runner; Node is not needed. Releases never reuse a cache.

## ADR-033 in brief: the Go runtime

Kuben 1.x was written in Rust. For 2.0 the hub and the cluster agent are rewritten in Go, the language of Kubernetes, k3s, Helm and cert-manager. The maintained Kubernetes, OCI and ACME libraries (client-go, controller-runtime, envtest, controller-gen) replace code we wrote and kept by hand; builds take seconds and cross-compile without extra tooling; and many more contributors can read and change the code. It is not a performance rewrite: speed is of the same order, and the agent uses more memory. Users should see no change, so the contracts stay frozen (along with the agent protocol, the configuration and the CLI), and the Go code is checked against them:

- **The API:** `packages/api-client/openapi.json` as 1.2 shipped it. The Go server is generated from it, and an oracle test compares the Go hub with the released 1.2.0 binary request by request.
- **The custom resources:** `charts/kuben/crds/kuben.dev_all.yaml`. The binary embeds the same bytes and the Go tests pin them; from 2.1 controller-gen generates the manifest from the Go types.
- **The SQL schema:** the migrations of 1.2, byte for byte. 2.0 adds none, so going back to 1.2 is an image change; the first new migration comes with 2.1.

The release keeps the archive names, checksums and signatures of 1.x, so `install.sh` and the chart work unchanged. 1.2.x receives security fixes from the `release/1.2` branch for six months after 2.0.

The full texts, with context and consequences, are in the repository under [`docs/adr/`](https://github.com/Teamtem-dev/kuben/tree/main/docs/adr).

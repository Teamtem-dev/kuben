The one-line installer puts a single `kuben` binary on Linux or macOS (x86_64 or arm64). The binary manages a cluster through a kubeconfig and keeps its own data in SQLite. It is the quickest way to try Kuben on one server, and a reasonable way to run it there.

<Aside type="tip">
For production inside a cluster, prefer the [Helm install](/docs/operations/production-install/): it runs Kuben with probes, RBAC, a persistent volume and the security context described in the security model.
</Aside>

## Install

```bash
curl -fsSL https://raw.githubusercontent.com/Teamtem-dev/kuben/main/install.sh | bash
```

Options, as flags or environment variables:

| Flag | Variable | Default |
|---|---|---|
| `--version v1.0.2` | `KUBEN_VERSION` | latest stable release |
| `--dir <path>` | `KUBEN_INSTALL_DIR` | `/usr/local/bin` |
| `--no-sudo` | `KUBEN_NO_SUDO=1` | uses `sudo` when the directory is not writable and `sudo` exists |

On Windows, download `kuben-x86_64-pc-windows-msvc.zip` from the [releases page](https://github.com/Teamtem-dev/kuben/releases).

### What the script guarantees

- **HTTPS only**, TLS 1.2 or later, no redirects to plain HTTP.
- **Checksum first.** The archive's SHA-256 is compared with the release's `checksums.txt` *before* anything is extracted or installed.
- **No partial execution.** The whole script is a `main()` called on the last line, so a truncated download runs nothing.
- **Native architecture.** An x86_64 shell under Rosetta on Apple Silicon still gets the arm64 binary.
- **No API calls.** The latest version is found through the `releases/latest` redirect, so there is no rate limit and no `jq`.
- **Verified after every release.** CI runs the script on Ubuntu (x64 and arm64) and macOS against the real release.

To go further, verify the build provenance with the GitHub CLI:

```bash
gh attestation verify kuben-x86_64-unknown-linux-musl.tar.gz --repo Teamtem-dev/kuben
```

## Run it on a server

<Steps>

1. Get a cluster to manage. On a single server, k3s is the quickest. It writes its kubeconfig for root only, so give your user a copy:

   ```bash
   curl -sfL https://get.k3s.io | sh -
   sudo install -D -m 600 -o "$USER" /etc/rancher/k3s/k3s.yaml ~/.kube/config
   export KUBECONFIG=~/.kube/config
   ```

2. Check the prerequisites. `doctor` checks the database, the cluster connection, Gateway API, cert-manager and metrics-server, and tells you what is optional.

   ```bash
   kuben doctor
   ```

   The `database` line shows where the data lives. Without `KUBEN_DATABASE__URL` it is `~/.local/state/kuben/kuben.db`, or the state directory under systemd's `StateDirectory=` (for example `/var/lib/kuben`). A server that already has `/data`, the container volume and the location before 1.0.3, keeps using `/data/kuben.db`. To choose yourself:

   ```bash
   export KUBEN_DATABASE__URL=sqlite:///srv/kuben/kuben.db
   ```

3. Start Kuben. The first start prints the generated admin password **once**, in this terminal. It is never written to the log.

   ```bash
   kuben serve
   ```

4. Open the console at `http://<server-ip>:8080`. The session cookie is not `Secure` until the console has an `https://` address: set `KUBEN_SERVER__PUBLIC_URL` once Kuben sits behind TLS and it becomes `Secure` on its own (`KUBEN_SECURITY__COOKIE_SECURE=auto`, the default). A plain-http console on a public address is fine for a first look, not for a team: put it behind HTTPS before inviting anyone.

</Steps>

## Keep it running

Run Kuben as its own system user, with its settings in `/etc/kuben/config.toml`: every command reads that file, so `kuben reset-admin` or `kuben backup` work on the same database as the service.

<Steps>

1. Create the user and give it the kubeconfig:

   ```bash
   sudo useradd --system --home-dir /var/lib/kuben --shell /usr/sbin/nologin kuben
   sudo install -D -m 600 -o kuben -g kuben /etc/rancher/k3s/k3s.yaml /var/lib/kuben/kubeconfig
   ```

2. Configure it:

   ```toml title="/etc/kuben/config.toml"
   [server]
   bind = "127.0.0.1:8080"
   metrics_bind = "127.0.0.1:9090"

   [database]
   url = "sqlite:///var/lib/kuben/kuben.db"

   [kube]
   kubeconfig = "/var/lib/kuben/kubeconfig"
   ```

3. Add the unit and start it:

   ```ini title="/etc/systemd/system/kuben.service"
   [Unit]
   Description=Kuben
   After=network-online.target k3s.service
   Wants=network-online.target

   [Service]
   ExecStart=/usr/local/bin/kuben serve
   User=kuben
   StateDirectory=kuben
   Restart=on-failure

   [Install]
   WantedBy=multi-user.target
   ```

   ```bash
   sudo systemctl daemon-reload && sudo systemctl enable --now kuben
   ```

4. Without a terminal, the first start writes the generated admin password to a file only `kuben` can read. Read it, sign in, and delete it:

   ```bash
   sudo cat /var/lib/kuben/initial-admin-password
   ```

   ```bash
   sudo rm /var/lib/kuben/initial-admin-password
   ```

   Run other commands as the same user, for example `sudo -u kuben kuben reset-admin`.

</Steps>

Binding to `127.0.0.1` keeps the console and the metrics off the public interface. Reach the console through an SSH tunnel, or put a reverse proxy that terminates TLS in front of it and set `public_url` under `[server]` to its `https://` address, which also makes the session cookie `Secure`. On k3s, Traefik already holds ports 80 and 443 on the host, so such a proxy needs Traefik disabled (`--disable=traefik`) or other ports. When a proxy sits in front, set `trust_forwarded_for = true` under `[security]` so login throttling sees real client addresses; see [Configuration](/docs/reference/configuration/).

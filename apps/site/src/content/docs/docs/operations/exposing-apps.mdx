## Routes

For every app with an HTTP port, the App controller creates an `HTTPRoute` in the environment namespace. Its hostnames are the app's custom domains plus `<app>-<environment>.<baseDomain>`. Processes with `protocol: tcp` (databases from templates) get a cluster-internal `Service` only.

Without `platform.baseDomain` and a Gateway (`platform.gatewayClassName` or `platform.gateway`), apps are reachable only inside the cluster.

## The Gateway

Kuben writes the listeners of **one** Gateway, and only of a Gateway that is its own:

- **Kuben creates it** when `platform.gatewayClassName` is set (for example `traefik` on k3s, or `eg` for Envoy Gateway). The Gateway is `kuben-system/kuben` unless `platform.gateway` names another one, and it carries the label `kuben.dev/gateway-owner=kuben`.
- **You dedicate an existing one** by naming it in `platform.gateway` and labelling it `kuben.dev/gateway-owner=kuben`.

Some Gateway controllers match a listener's port to one of their own entry points. Traefik, including the one k3s bundles, listens on 8000 and 8443, so set `--set platform.gatewayPorts.http=8000 --set platform.gatewayPorts.https=8443` there. Envoy Gateway and Cilium use the listener ports directly (the default 80 and 443).

Kuben never writes a Gateway without that label. It reports why on the `Gateway` condition of `KubenConfig` (`kubectl get kubenconfig kuben -o yaml`): `GatewayNotOwned`, `GatewayMissing`, `GatewayAPIMissing`, `GatewayClassNotAccepted`, `NotProgrammed`, or `Programmed` with the Gateway's address.

## Listeners

- **`http` (port 80):** with HTTPS, only the platform's redirect route and cert-manager's challenge routes may attach, and every other request is redirected to HTTPS. Without HTTPS, the routes of Kuben's namespaces attach here.
- **One HTTPS listener per hostname**, named `h-<hash>`, with the certificate Secret `kuben-tls-<hash>`. A hostname admits routes only from the namespace that claimed it first.
- **Optionally one wildcard listener** `https` for `*.<baseDomain>`, when `wildcardTlsSecret` is set. All generated hostnames then share it.

The Gateway gets the annotation `cert-manager.io/cluster-issuer`, and cert-manager's gateway-shim issues a certificate for every listener.

HTTPS is on only while the ClusterIssuer named in `clusterIssuer` is **Ready**. Kuben checks the cluster, not just the setting: until the issuer is Ready, apps are served over plain HTTP, their URLs say `http://`, and `kuben doctor` shows why.

## Dedicating an existing Gateway

To let Kuben create its Gateway, set `--set platform.gatewayClassName=traefik` and skip this section. To use a Gateway you manage yourself, create the shell and label it; Kuben fills in the listeners:

```yaml title="gateway.yaml"
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: kuben
  namespace: kuben-system
  labels:
    kuben.dev/gateway-owner: kuben
spec:
  gatewayClassName: traefik   # or eg (Envoy Gateway), cilium
  listeners:
    - name: http
      protocol: HTTP
      port: 80
```

Then reference it in the chart: `--set platform.gateway=kuben-system/kuben`.

## A ClusterIssuer that solves HTTP-01 through that Gateway

```yaml title="clusterissuer.yaml"
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: ops@example.com
    privateKeySecretRef:
      name: letsencrypt-account
    solvers:
      - http01:
          gatewayHTTPRoute:
            parentRefs:
              - kind: Gateway
                name: kuben
                namespace: kuben-system
                sectionName: http
```

cert-manager needs its Gateway API support switched on: `helm upgrade cert-manager … --set config.enableGatewayAPI=true`.

## Wildcard certificate

With many apps, one listener per generated hostname runs into the listener cap. Issue a **DNS-01** `Certificate` for `*.<baseDomain>` whose **name equals the Secret name** you put in `wildcardTlsSecret`; cert-manager then leaves it alone instead of trying HTTP-01 on the wildcard listener.

```yaml title="wildcard.yaml"
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: apps-wildcard          # == secretName
  namespace: kuben-system
spec:
  secretName: apps-wildcard
  dnsNames: ["*.apps.example.com"]
  issuerRef:
    kind: ClusterIssuer
    name: letsencrypt-dns       # a DNS-01 issuer
```

```bash
helm upgrade kuben oci://ghcr.io/teamtem-dev/charts/kuben -n kuben-system --reuse-values \
  --set platform.wildcardTlsSecret=apps-wildcard
```

## TLS per domain

Each custom domain of an app sets `tls`:

- **`auto`** (the default): a certificate from the ClusterIssuer, on a listener of its own. Generated hostnames are always `auto`.
- **`none`:** plain HTTP only. The hostname gets an HTTP listener of its own, so the platform's HTTPS redirect does not apply to it.
- **the name of a Secret** in the app's namespace: the app brings its own certificate. Kuben creates a `ReferenceGrant` named `<app>-tls` that lets the Gateway read exactly that Secret, and the listener uses it. cert-manager does not touch it.

The route carries its domains in the annotation `kuben.dev/domains`, so the Gateway gets the same listeners whether the App controller or the cluster's agent wrote the route.

## Honest limits

- A Gateway holds at most **64 listeners**; Kuben uses at most 60. Beyond that, use the wildcard listener for generated hosts. ListenerSet support (experimental in Gateway API) is on the roadmap.
- TLS termination happens at your Gateway controller. Kuben only configures it; it never handles app traffic.
- One Gateway per Kuben installation. The chart's optional `route` for the console can use the same Gateway.

## Status

Each app reports its exposure in the `Exposed` condition:

| Reason | Meaning |
|---|---|
| `RouteApplied` | the HTTPRoute exists and is attached |
| `NoGateway` | neither `KubenConfig.spec.gatewayClassName` nor `spec.gateway` is set; the `Gateway` condition of `KubenConfig` says more |
| `NoHostname` | the app has no domain and no base domain is configured |
| `GatewayAPIMissing` | the Gateway API CRDs are not installed |

The API reports reachability apart from health (an app can run and still be unreachable). Each app in `GET …/apps` and `GET …/apps/{app}` has an `exposure` object: `routed` says whether the Gateway accepted the route and resolved its references, and each host lists its `tls` mode and, for `auto` hosts, whether its certificate is issued (`certificateReady`, with cert-manager's message while it is not).

The **Check DNS** button (`GET …/apps/{app}/domains`) tells you whether each hostname already points at the Gateway. See [Custom domains and HTTPS](/docs/guides/custom-domains/) for the user-facing flow.

<Aside type="note" title="Which Gateway controllers are tested">
Kuben's end-to-end suite runs on kind with Traefik v3 as the Gateway provider and cert-manager, and checks every app over HTTPS from outside the cluster (no port-forward), including while Kuben itself is stopped. Envoy Gateway and Cilium implement the same Gateway API surface Kuben uses (listeners, HTTPRoute, `allowedRoutes` by namespace) and are expected to work; please report differences.
</Aside>

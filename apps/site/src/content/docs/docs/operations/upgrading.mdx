## Helm

```bash
helm upgrade kuben oci://ghcr.io/teamtem-dev/charts/kuben -n kuben-system --reuse-values
```

Add `--version 1.2.0` to pin a chart version; the chart's `appVersion` selects the image tag.

Two things that usually need care with operators are automatic here:

- **CRDs.** Helm does not update the `crds/` folder on upgrade. The binary therefore **server-side-applies its own CRDs on every start**, so new fields appear as soon as the new pod runs. Downgrading leaves newer CRD fields in place; they are ignored by older binaries.
- **Migrations.** Database migrations run at boot, under a lock, so several replicas starting together do not race.

The upgrade is a rolling update with `maxUnavailable: 0` and a leader hand-over: the controllers pause for a few seconds, the API not at all; see [High availability](/docs/operations/high-availability/).

## From 1.x

Kuben 1.x kept its data in SQLite. Kuben now keeps it in PostgreSQL only and does not open SQLite. The data of a 1.x install will be moved by an importer, which is not released yet.

- **Helm.** The `persistence.*` values and the SQLite volume `<fullname>-data` are gone from the chart; it runs its own PostgreSQL unless `database.url` or `database.existingSecret` is set. An upgrade of a release that still has the volume `<fullname>-data` (`kuben-data` for a release named `kuben`) stops with a message. Set `legacy.sqliteVolumeAcknowledged=true` to start with a new, empty database instead; the old volume stays untouched.
- **Server.** `kuben setup` stops when `/etc/kuben/config.toml` still names a SQLite database.

## Binary

Re-run the installer, optionally pinned:

```bash
curl -fsSL https://kuben.teamtem.com/install.sh | sh -s -- --version v1.0.2
sudo systemctl restart kuben
```

`kuben migrate` applies pending migrations without starting the server, if you prefer to run them as a separate step.

<Aside type="tip" title="Before upgrading">
Take a [backup](/docs/operations/backup-restore/): `kuben backup` plus a `pg_dump` of the database. Read the [release notes](https://github.com/Teamtem-dev/kuben/releases) for anything marked as a breaking change.
</Aside>

## Versioning

Kuben follows semantic versioning. The Helm chart version, the image tag and the binary version are the same number. Pre-releases (`v1.1.0-rc.1`) are published as GitHub pre-releases and never move the `latest` image tag.

Every release ships with checksums, build attestations and an image scanned before it is pushed; see [CI/CD and releases](/docs/contributing/ci-cd/).
